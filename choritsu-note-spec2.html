調律ノート仕様検討 第2版2026-08-10

台帳を核に据え、単発の仕事と、世界と、次の世代へ

前回の指摘6点に対する方針。「案内を送るアプリ」から「お客様とピアノの台帳」へ世界観を移し、単発案件・個人情報・事業承継・フリーミアム・海外展開までを一続きの設計として整理する。記録の修正はすでに実装ずみ。

実装ずみ記録の修正と取り消し

お客様詳細の履歴と、売上タブの記録一覧から、記録を直せるようにしました。日付・作業内容・料金・追加作業・支払方法・ピッチ・湿度・状態・メモを修正でき、取り消しもできます。日付を直すと、次回のご案内時期も自動で追随します。取り消したときは、ひとつ前の記録をもとに計算し直します。請求済み・入金済みの記録には警告を出します。

あわせて countsToCycle() という判定を先に入れてあります。次章の単発案件で、修理だけの訪問では調律の周期を動かさないために使います。

1単発の仕事を扱い、台帳を核にする

なぜ世界観を移すのか

いまのアプリは「調律の時期が来たピアノに案内を送るもの」として組まれています。しかし調律師の技術作業の内訳を見ると、調律は半分に届きません。

調律25%、修理20%、整調10%、整音1%、その他44% 調律師本人の記録より（前回調査で取得）

技術作業だけを取り出すと 調律45%／修理・整調・整音55%。定期調律だけを扱うアプリは、仕事の半分が見えません。台帳を核に据えれば、定期も単発も同じ場所に積み上がります。

効き目 1

売上の実像が映る。いまの売上タブは業務の一部しか集計していません。単発を入れて初めて、その月に本当にいくら稼いだかが分かります。

効き目 2

解約しにくくなる。データの持ち出し機能を作らない方針であれば、囲い込みは「台帳が厚いこと」で作るほかありません。単発も含めて全部が入っていれば、他へ移る理由が減ります。

効き目 3

新規のお客様の入口になる。「弦が切れた」で呼ばれた一見のお客様を台帳に入れ、そのまま定期調律のお客様に育てられます。いまは定期調律の人しか登録できません。

効き目 4

事業承継の価値が出る。渡すものが「案内の設定」ではなく「お客様との歩みの記録」になります（第5章）。

データ構造

記録に種別を持たせ、種別ごとに「調律の周期を動かすかどうか」を変えます。

// 作業の記録
record = {
  date, kind, pianoId, work, fee, works[], memo, cond, photo…, pay, bill
}

kind = "tuning"    定期調律   → 周期をリセットする
     | "repair"    修理       → 周期は動かさない
     | "regulate"  整調・整音 → 周期は動かさない
     | "check"     点検       → 周期は動かさない
     | "move"      運搬・移動 → 周期は動かさない（ピアノに紐づかない場合もある）
     | "other"     その他

// 訪問の予定にも種別と理由を持たせる
visit = { date, time, pianoIds[], kind, reason }

ここが肝です。修理だけで伺っても、調律の時期は動きません。いまの実装は無条件に「前回の調律日」を更新してしまうので、修理で行った翌月に「まだ調律していないのに次回は1年後」になってしまいます。

単発依頼を受ける流れ

1
お客様から連絡が来る電話・LINEなど、アプリの外で来ます。ここは変わりません。
2
「臨時の依頼を受ける」を押すお客様詳細から。新規のお客様なら、その場で登録します。ピアノが未登録でも受けられるようにします。
3
種別と理由を選ぶ修理／整調／点検／運搬／その他。理由は事前問診の選択肢を流用できます（「特定の鍵盤の音が出ない」など）。
4
予定に入る日付だけ決めて時間は後回し、という進め方も同じように使えます。ただし「時期を迎える」の一覧には出ません。周期を持たないので当然です。

台帳を核にするための画面

  • タブの並びは変えません。朝いちばんに見たいのは「今日どこへ行くか」で、それは変わらないからです。核になるのは思想であって、タブの順序ではありません。
  • お客様詳細に「この方との歩み」を置きます。お付き合いの年数、累計の訪問回数、累計の売上、定期と単発の内訳。台帳が資産であることを、数字で見せます。
  • 履歴をピアノ横断で1本の時系列にします。いまはピアノごとに分かれていますが、運搬のようにピアノに紐づかない仕事も出てきます。ピアノ別と顧客通しの両方を見られるようにします。
  • 売上グラフを種別で色分けします。「ご案内から生まれた売上」の分母からは、単発を外します。案内から生まれたものではないからです。
  • 記録フォームの冒頭で種別を選びます。既定は「定期調律」。単発のときだけ変える形にして、いつもの操作は増やしません。

3お客様の個人情報をどう預かるか

300人ぶんの氏名・住所・電話・メール、そしてお客様のお宅の写真を扱います。個人情報取扱事業者としての安全管理措置の義務がかかり、漏洩時には本人への通知と個人情報保護委員会への報告が必要です。個人開発でいちばん見落とされ、いちばん致命的になる部分です。

方針は4つ

その一　持たないものを決める

  • パスワードを持たない。メールのリンク認証かパスキーにします。パスワード漏洩という事故の種類そのものを無くせます。
  • カード情報を持たない。決済は Stripe などに丸ごと預け、自分のサーバーには一切通しません。
  • 写真は必要なぶんだけ。報告書に使うものに限り、保存期間を決めて自動で消します（たとえば3年）。持ち続けるほどリスクだけが増えます。

その二　同意の導線をつくる

お客様のお宅の中を撮ってクラウドに置くには、お客様の同意が要ります。報告書を初めてお送りするときの文面に、記録として写真を保存していること、不要ならお申し付けいただけることを入れます。お客様ごとに「写真の保存 : 同意／辞退」を持ち、辞退なら端末の中だけに置きます。

その三　消せるようにする

「私の情報を消してほしい」と言われたときの導線です。お客様詳細から、写真を含めて完全に削除できるようにします。削除したという事実だけは記録に残します（お名前は伏せて）。

その四　名乗る

プライバシーポリシーと利用規約をアプリの中から読めるようにし、問い合わせ窓口を明示します。漏洩が起きたときの手順（発覚 → 影響範囲の特定 → 本人への通知 → 委員会への報告）を、事が起きる前に決めておきます。

世界展開との関係

EU圏に出るなら GDPR への対応が参入条件になります。Gazelle が「GDPR Compliance」を機能一覧に掲げているのは、そのためです。日本の個人情報保護法への対応を、はじめから GDPR を見据えた形で作れば二度手間になりません。具体的には、保存先リージョンを選べる構造、削除要求の処理の流れ、データの取り扱い記録の3点です。

5引退を、解約ではなく引き継ぎにする

日本ピアノ調律師協会の会員数は10年で約3,000人から約2,000人へ減りました。年3〜4%が自然に減っている計算です。この減りは解約として現れます。これを「引き継ぎ」に変えられれば、契約は次の代へ生き残ります。

6フリーミアム ── どこで線を引くか

前回案の撤回

前回のマネタイズ案は「無料は30件まで、自動リマインドは必ず有料側に置く」でした。これは撤回します。自動リマインドこそが唯一の「買う理由」なので、それを有料に隠すと無料版の価値がほぼゼロになります。個人事業主のクラウド会計利用率が31%、つまり7割は有料ツールを使っていないという現実の中で、無料版が体験版でしかないなら最初の一人が獲れません。

機能ではなく「規模」で切る

無料でも失注防止が完結する。有料は「規模が大きくなると要るもの」に寄せる
　無料有料
お客様の数30軒まで無制限
ピアノ台帳・履歴・写真○○
調律時期の自動お知らせ○○
ご案内の送信・Web予約・見送り○○
作業報告書○（写真は1件1枚）○
単発の仕事の管理○○

この線引きの理屈

  • 無料で「失注防止」が完結します。買う理由を、まず無料で体験してもらいます。ここをケチると誰も使い始めません。
  • 有料は規模の機能に寄せます。30軒なら前日確定も繁閑の平準化も要りません。1日2軒なので、まとめて時間を決める場面がそもそも来ない。会計のCSVは、売上が立ってから必要になります。
  • 言い換えると、無料版は駆け出し・副業に十分、有料版は本業で回している人に必要という切り方です。
  • 30軒の根拠。ベテランで月30〜50件、年300〜600件、お客様300人が標準です。30軒は「始めたばかり」の規模で、本業なら必ず超えます。

価格

推奨

月額 1,480円 ／ 年額 14,800円（年額なら2ヶ月ぶん無料）。前回案の年19,800円から下げます。理由は3つ。個人サロン向け予約システムの相場が「予約のみで無料〜月3,000円」であること。調律1件が約13,000円なので、「調律1件ぶんの年会費」という説明がそのまま使えること。そして「年に1件つなぎ止めれば元が取れる」という言い方が、14,800円のほうが素直に成り立つことです。

無料ユーザーの費用をどう抑えるか

  • 費用の主は写真です。無料は1記録につき1枚まで、解像度も落とします。
  • 1年間ログインがなければ休眠扱いにします。データは保持しますが、通知は止めます。

8Android と、世界展開を見据えた設計

技術の方針は変えません

PWA を第一実装にします。1つのコードで Android・iOS・パソコンを同時にまかなえます。40〜60代は Android が約6割、70代は約7割（モバイル社会研究所 2026年1月調査）。検証機は AQUOS、画面幅360pxを基準にします。ストアに出す必要が生じたら、Capacitor で PWA を包めばプッシュ通知も使えます。

いま直さないと、後で高くつくもの

ここが本題です。データ構造に関わるものは、実際のお客様のデータが入る前に直すべきです。

最優先

住所の構造が日本の形に固定されています。いまは { 郵便番号, 都道府県, 市区町村, 番地, 建物 } です。国によって項目も並び順も違います（米国は state / city / street、英国には county があり、番地が先に来る国もある）。

{ country, postal, region, city, line1, line2 } という国際的な形に変え、表示のときだけロケールで組み替えます。これは今直さないと、後でデータの移行が必要になります。

商習慣が国で違うもの ── 設定で切り替える

  • 未調律期間の割増料金は日本固有の可能性が高い。機能としてオフにできるようにします。
  • 繁忙期の月は国と半球で逆転します。南半球は季節が逆です。設定できるようにするか、実際の予約データから学習させます。
  • 基準ピッチ。日本は A=442 が標準ですが、欧米は A=440 です。ロケールで既定値を変えます。
  • 税。消費税・VAT・Sales Tax は仕組みがまったく違います。内税か外税か、税率が複数あるかを設定で持ちます。
  • インボイスの登録番号は日本固有です。「税の登録番号」という汎用のラベルにします。

表示まわり

  • 文字列をコードから外に出します。いまは HTML と JavaScript に直接書かれています。
  • 日付は Intl.DateTimeFormat、金額は Intl.NumberFormat に委ねます。「2026年8月10日」「円」は日本語固有の表記です。
  • 「◯◯ 様」という敬称は日本語固有です。姓名の順序も国で違います。氏名は1つの項目のままにして、敬称はロケール側で付けます。
  • 右横書き（アラビア語圏）は優先度が低いものの、CSS で方向を切り替えられる構造にしておきます。

その他

  • ピアノのメーカー候補。YAMAHA・KAWAI は日本中心の顔ぶれです。欧州なら Steinway・Bösendorfer・Bechstein・Blüthner、米国なら Baldwin・Mason & Hamlin。候補をロケール別に持ちます。
  • ご連絡の手段。日本は LINE が主ですが、海外では SMS・WhatsApp・iMessage です。送信手段をロケールで切り替えられる構造にします。

まとめ ── 次に手を動かす順番

1記録に種別を持たせ、単発の仕事を扱えるようにする周期を動かす記録／動かさない記録を分ける。データ構造の変更なので、S層の作業と同じく後回しにすると全面改修になるいま
2住所の構造を国際的な形にする同上。実際のお客様のデータが入る前にいま
3お客様詳細に「この方との歩み」を置く累計売上・お付き合い年数・訪問回数。台帳が資産であることを数字で見せる次に
4無料と有料の線引きを画面に反映する30軒を超えたときの案内。無料版でも失注防止は完結させる次に
5お客様の引き継ぎ売り文句としては強いが、使われるのは数年先。仕組みだけ決めておけばよい後で
6個人情報の体制実際にお客様のデータを預かる前に。作るのはコードより文書と手順公開前

データ構造にかかわる 1 と 2 は、いま直すべきものです。それ以外は、実際の調律師に見てもらってからでも間に合います。
