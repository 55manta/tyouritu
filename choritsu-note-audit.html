重大データが黙って失われる

1写真を無加工で保存しており、7回の訪問でストレージが満杯になる重大
choritsu-note.html:4086–4100（bindPhoto）／ 4016–4017（entry）

カメラで撮った写真を readAsDataURL でそのまま文字列にし、縮小せずに localStorage へ入れています。仕様書には「長辺1280px・WebPに縮めてから送る」と書かれていますが、その処理はコードのどこにもありません。スマホの写真1枚は無加工で約4MB、data URL にすると約5.3MBです。

無加工なら 11枚、長辺1280pxに縮めれば 392枚 入る
効き方
これは「写真が保存できない」で済みません。状態全体を1つのJSONとして書いているため、写真1枚が溢れた瞬間に、台帳そのものの保存が止まります。お客様の登録も、記録も、以後いっさい永続化されません。しかも画面は正常に動き続けます。

測ったのはデスクトップのChromeです。iOS Safari の localStorage はこれよりずっと小さく、写真1枚で溢れます。つまり実機では、この欠陥はもっと早く出ます。

直し方
移植先では写真を Firebase Storage に置き、DBにはURLだけ持たせます（アーキテクチャ仕様どおり）。撮影直後に expo-image-manipulator で長辺1280pxに縮めます。この構造にすれば問題ごと消えます。
ただし
オフラインで撮った写真は端末に貯めて後で送るため、送信待ちの写真の総量に上限を設ける必要があります。ここは移植時に設計が要ります。
2保存の失敗を握りつぶしている重大
choritsu-note.html:1455
function save(s) {
  try { localStorage.setItem(KEY, JSON.stringify(s || state)); }
  catch (e) { /* 何もしない */ }

所見1と根は同じですが、これは独立した欠陥です。写真を縮小しても、この catch が空である限り「保存に失敗したのに成功したと見える」構造は残ります。調律師は「記録しました。次回は2027年8月ごろです」というトーストを見て、記録できたと信じて次の現場へ向かいます。

効き方
顧客台帳を預かるアプリで、失敗を黙って捨てるのは最も危険な作りです。失注を防ぐための道具が、記録の消失に気づかせないまま動き続けます。
直し方
保存の失敗は必ず画面に出す。移植先では書き込みが非同期になるので、成功を待ってからトーストを出す（楽観的にトーストを先に出さない）。
3忘れていた過去の調律を後から入力すると、次回のご案内時期が壊れる重大
choritsu-note.html:4028–4029（saveRecord）／ 2144–2148（recalcPianoLast）

このアプリには、周期の基準日 last を決める処理が2つあり、片方が間違っています。

// 記録の「修正・取り消し」のとき — 正しい。履歴の中で最も新しい調律を採る
function recalcPianoLast(p) {
  sortHistory(p);
  var base = p.history.filter(countsToCycle);
  if (base.length) p.last = base[0].date;
}

// 記録の「新規保存」のとき — 入力された日付を無条件に採ってしまう
if (countsToCycle(entry)) {
  recPiano.last = date;   ← 過去の日付でも上書きされる
}

実際に両方の経路を走らせて挙動を比べました。2026年8月1日に調律を終えたピアノについて、去年6月にやった記録の入力漏れに気づいて後から足す、という場面です。

画面での見え方2週間前に調律したばかりのピアノが「時期を過ぎています」の一覧に並ぶ。そのまま案内を送れば、お客様に「先月やったばかりですよ」と言われる
効き方
記録の入力漏れを後から埋めるのは、現場でごく普通に起きる操作です（作業直後は手がふさがっており、後でまとめて入れる運用は仕様書自身が想定しています）。しかも間違った結果が「時期を過ぎています」という行動を促す表示として出るため、誤った案内送信に直結します。
直し方
1行です。recPiano.last = date を recalcPianoLast(recPiano) に置き換え、基準日を決める場所を1箇所に統一します。
移植では
アーキテクチャ仕様で決めた「記録を書く唯一の関数（src/lib/cycle.ts）」が、まさにこの種の分岐を防ぐための規律です。この所見は、その規律が必要だという実例そのものです。

4調律の記録を全部取り消すと、基準日が宙に浮く要修正
choritsu-note.html:2147

if (base.length) p.last = base[0].date; ——調律の記録が1件も残らなかったとき、last は更新されません。取り消したはずの記録の日付が、周期の基準として残り続けます。修理の記録だけが残ったピアノで実際に再現しました。

直し方
ピアノ登録時に入力させている「前回の調律日」を別の項目として保持し、調律記録が無いときはそこへ戻す。いまは同じ last を上書きしているため、戻る先がありません。

「3ヶ月後に様子を見に来ます」という一度きりの再訪のつもりで日付を入れると、そのピアノは以後ずっと3ヶ月周期のピアノとして扱われます。年1回のはずのお客様に、年4回の案内が出るようになります。

直し方

6お客様もピアノも、削除する手段が存在しない要修正
choritsu-note.html 全体（該当コード無し）

削除に相当する機能をコード全体で探しましたが、1つもありません（サンプルデータの一括消去は別）。誤って登録したお客様を消せません。

法令
これは使い勝手の問題にとどまりません。仕様書は自ら「『私の情報を消してほしい』と言われたときの導線。お客様詳細から、写真を含めて完全に削除できるようにします」と書いています。個人情報取扱事業者としての義務に直結する部分が、丸ごと未実装です。
直し方
論理削除（deletedAt）と、写真を含む物理削除の2段を用意する。アーキテクチャ仕様のデータ設計には deletedAt を入れてあるので、画面と導線だけが不足しています。

以下は「バグ」ではなく、仕様書では決定ずみなのにコードに存在しないものです。モックを忠実に移植すると、決めたはずの設計が抜け落ちます。

7無料15軒の線引きが、どこにも実装されていない実装の穴

プラン・上限・課金に関する処理をコード全体で探しましたが、該当なし。収益モデルの中核がまだ画面に存在しません。

論点
移植時に決める必要があります：16軒目でどう振る舞うか（登録を止めるのか、読み取りだけ許すのか）、既存のお客様が15軒を超えている状態でプランが切れたらどうするか。とくに後者は、実際の調律師が300軒を持っている以上、必ず起きます。
8お客様用の予約URLが、推測できてしまう作りになっている実装の穴
choritsu-note.html:1848
function bookingUrl(c) {
  return "https://choritsu-note.app/b/" + String(c.id).slice(1, 7);
}
// c.id = "c" + Math.random().toString(36).slice(2,9)

トークンがお客様IDそのもので、しかも6文字、生成元は Math.random() です。アーキテクチャ仕様には「推測できない長さで、有効期限を持たせます」と書きましたが、モックはそのどちらも満たしていません。

  • 失効できない。トークンがお客様IDと同一なので、LINEを転送されたら第三者が恒久的にそのお客様の予約ページを開けます
  • 総当たりの余地。6文字（約22億通り）を静的ページに置くと、回数制限が効きません
  • Math.random() は暗号用途向けではありません。複数のURLから内部状態を推定される可能性があります
効き方
この先にあるのはお客様の氏名・住所・ピアノ・訪問予定です。モックとしては問題ありませんが、そのまま移植してはいけない箇所として印を付けておく必要があります。
直し方
サーバー側で生成する十分な長さの乱数（crypto 由来）とし、顧客IDから切り離す。有効期限と失効を持たせる。
9写真の同意、プライバシーポリシー、問い合わせ窓口が無い実装の穴

仕様書が「方針は4つ」として挙げた個人情報まわりのうち、コードに存在するものはありません。photoConsent に相当するフラグもありません。お客様のお宅の中を撮った写真を、同意の記録なしに保存している状態です。

いつ
コードよりも文書と手順が主です。実際のお客様のデータを預かる前——クローズドテストに実データを入れる前——に用意する必要があります。

訂正アーキテクチャ仕様のほうを1点直します

前回の仕様書の修正

アーキテクチャ仕様（第3版）で、ピアノに nextDueOn を非正規化して持たせ、「時期を迎えたピアノ」をその1本のクエリで出す、と書きました。監査の過程で、これは行き過ぎだと分かりました。

いまのモックは dueDateP(p) をその都度計算しています。計算値である以上、ズレようがありません。保存された項目に変えると、いま存在しない「ズレる」という故障モードを新たに持ち込むことになります——所見3・4は、まさに保存された last がズレる話でした。

訂正後の方針。1人の調律師が持つピアノはせいぜい500台で、全部読んでも150KB程度です。アプリの画面はモックと同じく計算で出します。nextDueOn を持たせるのはサーバーの毎朝の通知処理のためだけ——全調律師のピアノを横断で走査する必要があるのは、そこだけだからです。こうすると、万一ズレても影響は通知のタイミングに限られ、画面の表示は絶対に狂いません。夜間の照合で直せば足ります。

アーキテクチャの方針を変える必要はありません。見つかった9件のうち6件は、Expo + Firebase への移植で構造ごと解消するか、移植時に自然に手が入る箇所です。いまモックで直す価値があるのは所見3と4——基準日を決める場所の統一だけです。これは移植先にそのまま持ち込む業務ロジックなので、間違ったまま写すと同じバグを引き継ぎます。
