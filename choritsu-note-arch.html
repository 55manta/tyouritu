調律ノート実装アーキテクチャ 第3版2026-08-27

調律ノートを、二本目のアプリとして作る

前回の技術仕様（2026-08-10）は Capacitor と Supabase を選び、「Mac の手配が最優先」と書いた。その前提は、いま調べ直すと成り立たない。割ペイはすでにこの Windows 機から iOS ビルドを出し、App Store で公開されている。調律ノートは白紙から始めるのではなく、すでに回っている生産ラインに乗せる二本目として設計し直す。

先に結論は3つ

前提が変わった

Mac は要りません。割ペイ（jp.izumikawa.warikan）は Expo + EAS Build で構成され、App Store に公開ずみです。EAS はクラウドの macOS でビルドするので、Windows のまま iOS を出せます。前回仕様書が「いま手配が要る／最優先タスク」と赤で囲んだ項目は、すでに解決ずみだったということです。

採用する構成

Expo（React Native）＋ Firebase ＋ RevenueCat。Capacitor と Supabase は採りません。理由は一つで、この4つ（EAS・RevenueCat・Firebase・両ストアのアカウント）を、すでに動かしているからです。二本目のアプリが新しい道具立てを持ち込む理由がありません。

日程を握るもの

Google Play の「12人×14日」は、アカウント単位ではなくアプリ単位です。割ペイでこの要件を通しても、調律ノートは免除されません。しかも割ペイ自身がまだ Play で公開に至っていない（ストアページが出ない＝クローズドテスト中）。調律ノートも、最小ビルドを最初にクローズドテストへ投入して14日のカウントを先に回す——ここだけは前回仕様書の判断がそのまま生きます。

6ひとつだけ割ペイと変える ── Firebase SDK

割ペイは Firebase の JS SDK（firebase パッケージ）を React Native で使っています。調律ノートでは @react-native-firebase（ネイティブ SDK）を採ります。理由は一つで、オフラインです。

確認した事実

Firebase JS SDK の Firestore オフライン永続化は、React Native では動きません。永続キャッシュは IndexedDB に依存しており、React Native に IndexedDB が無いためです。persistentLocalCache を指定してもエラーを出してメモリキャッシュに落ちます。Firebase 公式も「オフライン永続化に対応するのは Android・iOS・Web」＝ネイティブ SDK か Web、と明記しています。

割ペイの src/firebase/config.ts は initializeFirestore(app, { ignoreUndefinedProperties: true }) のみで、キャッシュ指定がありません。つまり割ペイは現状オフライン永続化を持っていないということです。割ペイは電波のある場所で使う前提なので問題になっていませんが、調律ノートは違います。

調律師はお客様のお宅の中——鉄筋の集合住宅、地下の音楽室、学校の講堂——で1台2〜3時間作業します。電波が弱い場所で「今日の訪問先が開けない」は、このアプリでは致命傷です。ネイティブ SDK に替えると、読み取りキャッシュも、オフライン中の書き込みキューも、再接続時の送信も、SDK が面倒を見ます。

方式オフライン読みオフライン書き追加の実装判断
@react-native-firebase○ 自動○ 自動ほぼ無し採用。config plugin と開発ビルドが要るが、どちらも割ペイで運用ずみ
JS SDK ＋ 自前キャッシュ△ 手作り△ 手作り300〜400行割ペイと API が完全一致する利点はあるが、キュー・競合・再送を自前で持つことになる
JS SDK のみ××無し現場で開けない。要件を満たさない

代償は、Auth・Storage も含めて Firebase まわり一式をネイティブ SDK に揃える必要があること（JS SDK と混在させると認証状態が二重になります）。ただし @react-native-firebase のモジュラー API は JS SDK とほぼ同じ形なので、割ペイのコードを読み替える負担は小さく済みます。

7データ設計

前回仕様書の Postgres スキーマを Firestore に写します。全データが「1人の調律師が所有する木」の下に入る——この形にすると、セキュリティルールが1行で書けて、しかも最も強くなります。

// すべて調律師の uid の下。他人のデータと交差しない
/tuners/{uid}                     屋号・資格・車番・税番号・locale・plan
  /customers/{customerId}         氏名・種別・連絡先・住所(国際構造)・photoConsent
  /pianos/{pianoId}               customerId を持つ。設置場所・製造番号・料金・周期
  /visits/{visitId}               customerId・pianoIds[]・日付・時刻(null可)・kind・問診
  /records/{recordId}             customerId・pianoId?・visitId?・kind・料金・状態・写真

/bookings/{token}                 お客様用ページ。認証なしで読める唯一の場所

// ピアノに1つだけ非正規化した項目を持たせる。これが要
piano.nextDueOn  = lastTunedOn + intervalMonths
// 「時期を迎えたピアノ」は、これ1本のインデックス済みクエリで出る
where('nextDueOn', '<=', today)
設計上のいちばんの勘所

前回仕様書は「kind='tuning' のときだけ last_tuned_on を更新する。DB のトリガーで守るのが安全」と書きました。Firestore にトリガーはありません。代わりに、src/lib/cycle.ts に記録を書く唯一の関数を置き、そこだけが lastTunedOn と nextDueOn を触れるようにします。画面から直接 setDoc を呼ばない、という規律で守る形です。セキュリティルール側でも種別と更新項目の整合を検証し、二重にします。

セキュリティルール

match /tuners/{uid} {
  allow read, write: if request.auth != null && request.auth.uid == uid;
  match /{col}/{doc} {
    allow read, write: if request.auth != null && request.auth.uid == uid;
  }
}

割ペイは「リンクを知っている人は誰でも読み書きできる」という設計です（招待リンクで参加する仕様なので、それが正しい）。調律ノートは正反対で、所有者以外は一切触れません。300人ぶんの氏名・住所・お宅の写真を預かるので、ここは厳しい側に振ります。

運用で必ず踏む

ルールを書き換えたら Firebase Console で「実際にデプロイされているルール」を確認してください。ローカルの firestore.rules が正だと思い込むと、permission-denied の原因を延々コード側で探すことになります（割ペイで実際に起きた事故です）。

8お客様用ページ ── ここだけ1ソースから外す

ご案内メッセージのリンクから開く /b/{token} は、アプリのコードベースに入れず、Firebase Hosting の静的ページとして別に作ります。「1ソースで」という方針からの、意図的な例外です。

  • 画面が1枚しかない。日付を選ぶボタンと「今回は見送る」ボタンだけ。ここに React Native Web のバンドルを送り込むのは釣り合わない
  • 開くのは高齢のお客様で、年に1回。LINE から開いて数秒で表示されないと離脱する。軽さがそのまま成約率になる
  • 認証がない場所を、アプリ本体と混ぜたくない。公開面を小さく切り離しておくほうが、守るものが減る

トークンは推測できない長さで、有効期限を持たせます。ここで日付を選ぶと visits に「日付確定・時間未定」の予定が生まれ、「今回は見送る」を押すと該当周期に見送りの印が立ちます。
